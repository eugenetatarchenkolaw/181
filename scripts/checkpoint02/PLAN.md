# План переиспользуемых скриптов

[Задание этапа](../../docs/checkpoints/checkpoint-02.md) · [Формат данных](../../data/checkpoint02/SCHEMA.md)

Это контракты будущей реализации. Перечисленных ниже Python-файлов пока нет, команды их запуска ещё не опубликованы. Документ нужен, чтобы начать с проверяемой небольшой задачи и затем использовать тот же код в сервисе.

## Порядок реализации

| Будущий файл | Вход | Выход | Первая проверка |
|---|---|---|---|
| `extract_references.py` | Один локальный основной PDF, `parent_id` | Строки библиографии с номерами и исходным текстом | Сверить весь список с PDF; сохранить ошибки извлечения |
| `collect_references.py` | `parents.csv`, `papers.csv`, `references.csv`, настройки источников | Дополненные метаданные и статусы, PDF, `download_attempts.jsonl` | Успех по DOI, неоднозначное название, недоступный PDF и повтор запуска |
| `extract_page_text.py` | Полученные PDF | Текст по страницам, версия извлечения и хеши | Открыть несколько страниц и сравнить с текстом, проверить двухколоночную вёрстку |
| `validate_dataset.py` | Папка CSV/JSONL и локальные файлы | Отчёт о нарушениях; ненулевой код завершения при ошибках | Обнаружить неверный parent, отсутствующий PDF, ошибочную страницу и пустой ответ |
| `summarize_corpus.py` | Проверенные манифесты и разметка | Сводные таблицы для отчёта | Сверить числа вручную на одной основной статье |

Сначала реализуется один полный путь на одной статье, затем он применяется к остальным. Автоматическая генерация вопросов не обязательна: они могут быть подготовлены вручную. Если она добавляется, её результат всегда сохраняется как `draft`.

## Контракт сборщика

Скрипт проходит всю библиографию каждого родителя. Для одной записи порядок такой:

1. Считать исходный текст, известные DOI/arXiv ID и результат предыдущих попыток.
2. Если есть проверенный PDF с тем же хешем и допустимой версией, сохранить событие `cached` и продолжить.
3. Если идентификатор известен, запросить метаданные и проверить соответствие записи. Иначе искать кандидатов по названию, авторам и году.
4. При нескольких правдоподобных совпадениях сохранить `ambiguous`; не скачивать произвольно выбранную статью как подтверждённый источник.
5. Для подтверждённой публикации искать доступный полный текст. Проверить arXiv-версию, открытое размещение по DOI или ссылку издателя в пределах разрешённого способа доступа.
6. Скачать файл с таймаутом и ограниченным числом повторов. Проверить, что получен открываемый PDF; вычислить SHA-256.
7. Сохранить конечный статус и события независимо от успеха. Ошибка одной записи не останавливает весь корпус.

Отдельные функции должны отвечать за запрос метаданных, выбор совпадения, поиск файла, загрузку и запись результата. Тогда HTTP-вызовы можно подменить сохранёнными ответами в тестах, а логику повторно использовать в worker.

## Устойчивость и настройки

Конфигурация содержит источники метаданных, ограничение частоты по каждому сервису, таймауты, число повторов, максимальный размер файла и каталоги данных. Контакт для вежливых API-запросов и ключи передаются через окружение; их нельзя печатать в журнал или сохранять в Git.

- Повторять только временные ошибки: ограничение запросов, таймаут и согласованный набор 5xx. Учитывать `Retry-After`.
- Записывать файл сначала во временный путь и переносить после проверки. Прерванная загрузка не получает статус `downloaded`.
- Сохранять оригинальные ответы API в локальный кэш без секретов; указывать дату и источник.
- Продолжать обработку с места остановки; не считать временный сбой окончательным отсутствием публикации.
- Проверять адреса после перенаправлений. Будущая серверная версия не должна скачивать произвольные внутренние адреса.
- Явно учитывать ручные исправления. Автоматически менять подтверждённую человеком связь без журнала нельзя.

## Минимальные осмысленные проверки будущего кода

Тесты появятся вместе с реализацией. Нужны случаи, в которых незаметная ошибка испортит данные: неверное сопоставление похожих названий, HTML вместо PDF, одна статья в библиографиях двух родителей, повтор после сбоя и вопрос с доказательством от чужого источника. Проверка живого API отделяется от воспроизводимых тестов на сохранённых ответах.

Набор не должен зависеть от Colab-сессии. В Colab допустимо запускать тот же код для удобства, но функции и настройки сохраняются в репозитории, а инструкция описывает запуск с чистого окружения.

## Что автор должен суметь объяснить

Почему выбран именно этот DOI; чем отличается отсутствие открытого файла от сетевой ошибки; как обнаружен дубликат; что произойдёт при повторном запуске; откуда взялся эталонный ответ; почему фрагмент достаточен для вопроса. Если какой-либо участок кода остаётся непонятным, его нужно разобрать и упростить до сдачи.
